## 為什麼會有這份文件

`regimes.status`/`origin_transition_type` 原本直接存憲法 §4 的中文術語（存續/分裂/被取代(禪讓)/被滅亡），套用的心智模型是中原「天命觀／朝代週期」。使用者提出疑慮：這套邏輯若原封不動套到羅馬、歐洲封建、伊斯蘭世界，資料模型會不會碰壁？2026-08-28 已將 `status`/`origin_transition_type` 改為文化中立代碼（`active`/`split`/`succeeded`/`conquered`），憲法本身業務詞彙不變（見 PRD §6 設計原則、implementation plan 第四次事後補充）。這份文件記錄當時逐一比對四大文明後的結論，供 M4 規劃時延續。

## 一、使用者原始整理：四大文明政權底層邏輯

### 1. 中原文明：天命觀與「朝代週期（Dynastic Cycle）」

- **核心合法性來源**：「天命（Mandate of Heaven）」與「德」。
- **政權本質**：天下唯有一主（天子）。政權是有壽命的（朝代興衰），失德則天命轉移。
- **權力轉移形式**：
  - 暴力革命（湯武革命）：武力推翻前朝（如秦滅六國、漢滅秦）。
  - 形式合法移轉（禪讓）：權臣架空後，逼前朝「自願讓位」以承接正統（如漢禪魏、魏禪晉、宋受後周禪）。
- **在 GIS 上的特徵**：通常有清晰的「朝代起訖年代」，邊界是中央朝廷朝貢體系或直接設郡縣的實質管轄。

### 2. 古羅馬與拜占庭：元首共和遺緒與「軍事擁立」

西方（羅馬體系）完全沒有「禪讓」概念，因為羅馬本質上從未自稱是「私家天下的王朝」。

- **核心合法性來源**：「元老院與羅馬人民（SPQR）」的認可 + 軍隊效忠。
- **政權本質**：羅馬皇帝（Imperator/Augustus）在名義上是國家第一公民（Princeps）或最高統帥，而不是中原那種「承奉天命的家族」。皇位理論上不是私產，因此羅馬帝國在法律上是同一個國家持續了千年，學者劃分的「王朝（如塞維魯王朝、巴列奧略王朝）」只是現代歷史學為了方便標記哪個家族在掌權。
- **西方類似「讓位」的特例**：戴克里先退位（西元 305 年）——四帝共治時期，戴克里先主動退位隱居去種萵苣，並指定副手接班。這不是把天下送給另一個家族的「禪讓」，而是帝國官僚體系的職位交接。
- **權力轉移形式**：
  - 養子繼承（收養制）：五賢帝時期，皇帝不傳子，而是收養最有能力的將軍/執政官為嗣子。
  - 禁衛軍／軍團叛變（軍人政變）：軍隊殺掉前任皇帝，直接黃袍加身（拍賣皇位或軍營擁立）。拜占庭帝國有大量皇帝是靠刺瞎前任、送進修道院而登基的。

### 3. 中世紀歐洲封建：神授君權與「血統契約（采邑制）」

- **核心合法性來源**：天主教會加冕（神授） + 純粹的家族血統法則（如薩利克法）。
- **政權本質**：領土與爵位是貴族家族的私有財產與契約關係。「我附庸的附庸，不是我的附庸」。
- **沒有禪讓的原因**：國王不能把王位「讓」給外姓，因為王位是上帝賦予該血脈的法定繼承權。如果要換家族，只有兩種途徑：
  - 絕嗣（Extinction）：國王死後無合法男性後代，各國貴族依聯姻母系血統爭奪繼承權（因此引發英法百年戰爭、西班牙王位繼承戰爭）。
  - 教宗廢黜／貴族政變：如矮子丕平廢黜墨洛溫王朝末王（進修道院），獲得教宗加冕開啟卡洛林王朝。
- **在 GIS 上的特徵**：疆域極度破碎且常因婚姻/遺產分割而劇變（例如哈布斯堡家族靠結婚吃下半個歐洲；查理曼帝國死後直接被三個孫子切成三份，演變成德法意雛形）。

### 4. 伊斯蘭世界：哈里發體系與「烏瑪共識／部落推舉」

- **核心合法性來源**：先知穆罕默德的繼承者（哈里發 Caliph） + 伊斯蘭教法（Sharia）。
- **政權本質**：全體穆斯林社群（烏瑪 Ummah）的宗教與世俗領袖。
- **權力轉移形式**：
  - 推舉／協商（舒拉 Shura）：正統哈里發時期（四大哈里發），由長老會議推舉產生（非世襲）。
  - 家族世襲但伴隨血統內戰：伍麥亞王朝（白衣大食）、阿拔斯王朝（黑衣大食），雖然是家族世襲，但內部常以「誰的血統更接近先知家族（聖裔）」或宗教正統性發動聖戰推翻前朝。
  - 蘇丹架空哈里發：中後期塞爾柱土耳其、馬木路克興起，「蘇丹（世俗軍事統帥）」架空「哈里發（名義宗教領袖）」，類似日本幕府將軍架空天皇。

## 二、與現有 schema 逐項比對（2026-08-28 分析）

關鍵區分：**「政權層級的轉移」**（`regimes` 這個實體本身終止/誕生）vs **「統治者層級的更迭」**（政權不變，換了誰在位）。`regimes.status`/`origin_transition_type` 這個狀態機設計上只管前者；後者屬於敘事層級，落在 `historical_events`。用這條界線重新分類上表：

| 使用者描述的機制 | 層級 | 對應現有機制 | 需要新結構？ |
|---|---|---|---|
| 中原：禪讓、覆滅、分裂 | 政權層級 | `status`＝`succeeded`/`conquered`/`split` | 不需要，設計基礎案例 |
| 羅馬：戴克里先退位、養子繼承、軍團弒君 | 統治者層級（羅馬帝國本身沒變，只是誰在位變了） | `historical_events`（敘事），不動 `regimes` | 不需要 |
| 羅馬：395 東西羅馬分裂、476 西羅馬滅亡、1453 拜占庭滅亡 | 政權層級 | `split`／`conquered` | 不需要，直接對應 |
| 歐洲：矮子丕平廢梅羅文加、教宗敕封卡洛林 | 政權層級，性質接近禪讓（廢王送修道院而非處死） | `succeeded` | 不需要——這正是把「禪讓」改成中立代碼 `succeeded` 的價值所在：不同儀式（中國禪讓 vs 教宗敕封）都是「非武力政權更替」，中立代碼裝得下，原本的中文字面值裝不下 |
| 歐洲：查理曼帝國三分（凡爾登條約） | 政權層級 | `split` | 不需要，結構上等同 seed 資料的「漢→魏/蜀漢/吳」三分 |
| 歐洲：聯姻共主（哈布斯堡）、伊斯蘭：蘇丹架空哈里發 | **不是轉移，是兩個政權並存的持續關係** | `regime_relations`（已存在，`relation_type` 自由文字） | 不需要——這個關係跟日本幕府架空天皇是同一種資料形狀 |
| 伊斯蘭：舒拉推舉哈里發 | 統治者層級（哈里發國本身沒變） | `historical_events` | 不需要 |
| 伊斯蘭：阿拔斯革命推翻伍麥亞 | 政權層級，武力推翻 | `conquered` | 不需要 |
| 伊斯蘭：白衣大食/黑衣大食 | 命名機制 | `regime_aliases`——同一政權在不同時期/觀察者眼中的代稱，跟「阿拉伯帝國在唐朝視角下叫大食」同一種資料形狀 | 不需要，直接驗證既有設計 |
| 學者劃分的「王朝」（如塞維魯王朝）標記哪個家族在掌權 | 史學家敘事分期，非客觀政權分類 | `lineage_presets`（方案 D）——核心政權圖保持中立，「哪個家族在哪段時間主導」是史觀呈現層 | 不需要，這正是方案 D 存在的理由 |

### 結論：現有 M1 schema 不需要因此重新設計

四文明的差異，絕大部分落在「統治者如何產生」（Shura 推舉、養子繼承、軍團擁立、貴族血統）這個 `historical_events` 敘事層級能吸收的範圍，或是「兩個政權間的持續關係」（`regime_relations` 已支援）。真正會撞到「政權」這個實體邊界的轉移形式（分裂、武力推翻、和平轉移），中原案例已經涵蓋。

## 三、真正需要 M4 前處理的缺口

**與上一輪（文化偏頗檢視）已追蹤的缺口相同，未發現新的 schema 級缺口**：

- [ ] `predecessor_regime_id` 是單一 FK，只能表達「一對多分裂」，無法表達「多對一合併」。歐洲封建的聯姻共主如果後來正式合併成單一政權（例如英格蘭+蘇格蘭→大不列顛），會撞上這個缺口——哈布斯堡聯姻案例只是同一問題的另一個例證，不是新問題。詳見 PRD §9 風險表、§12「M4 前必須處理」。

## 四、值得記錄、但現在不用動的開放問題

**「政權身份」與「統治家族」現在焊在同一個 `regimes` 實體裡**：中國史剛好兩者重合（漢＝劉家，換家族＝換政權），不會碰到這個問題。羅馬／哈里發這種「政權本身連續存在千年，只是統治家族換了好幾輪」的情況，現有設計沒有獨立的「統治家族」概念。

- **是否需要為此開新表**：地圖層級（政權疆域）不需要這個資訊——羅馬帝國的疆域形狀不會因為換了個家族在位就改變。只有敘事層級（誰在哪段時間統治、哪個「王朝」標籤）需要，現階段用 `historical_events` 描述已經夠用，不必為了羅馬預先加表。
- **M4 grill-me 時再問**：如果實際建置羅馬/拜占庭資料時發現「哪個家族在位」這個資訊真的需要被查詢/篩選（不只是敘事文字），才需要評估要不要加一張類似 `reign_eras` 的「ruling house」查詢表。現在只是標記，不預先設計。

## 五、使用者第二輪整理：宗教作為政權的「作業系統」

延續上一輪，使用者進一步指出「宗教/意識形態是古代政權的作業系統」，並補充東亞漢字文化圈內部的分化，以及提出具體 schema 提案。

### 東亞漢字文化圈的內部分化

- **朝鮮半島與越南（事大主義與「外王內帝」）**：政權變遷內部同樣講究天命與禪讓/革命，但外交上須獲中原皇帝冊封才能確立最終合法性。越南對中原自稱「安南國王」，對內百姓則自稱「大越皇帝」——雙重身份，適合套用憲法 §6「多重視角命名」機制。
- **日本（萬世一系與「雙首長制」）**：吸收儒家/法家制度但拒絕「易姓革命」，主張皇統血統神授（天照大神後裔），名義上從未改朝換代。武士崛起後發展出「雙首長制」——天皇在京都掌宗教/象徵權力（虛君），幕府將軍掌實質軍政大權，狀態機上是「實權架空與幕府更迭」的獨立類型。

### 西方演進是繼承融合，非平行文明

羅馬（城市/元老院/羅馬法/常備軍）→ 日耳曼（部落聯盟南下滅西羅馬後，吸收基督教+羅馬官僚體系，結合部落效忠約定，演化出歐洲封建制度）→ 北歐/維京（10-11 世紀為與歐陸通商及鞏固王權皈依基督教，定居諾曼第/英國/基輔羅斯後同化進歐洲封建與基督教體系）。使用者結論：不需要為日耳曼/北歐發明全新底層邏輯，早期屬性是「部落聯盟」（疆界模糊、隨意遷徙），皈依基督教後狀態機切換成「封建王國」。

| 文明體系 | 政權作業系統（Legitimacy OS） | 誰代表最高權力？ | GIS 地圖上的疆域特徵 |
|---|---|---|---|
| 中原/東亞 | 天命與儒家禮教 | 皇帝（天子）代表上天統治世俗 | 疆界相對明確，核心區極度穩定 |
| 中世紀歐洲 | 基督教與君權神授 | 權力二元論：教皇（靈魂）+ 國王/皇帝（肉體），常打架 | 疆域極度破碎，像拼圖一樣因聯姻/繼承權頻繁重組 |
| 伊斯蘭世界 | 伊斯蘭教法 | 哈里發（政教合一）：既是世俗君主也是宗教領袖 | 疆域隨聖戰迅速擴張，常因宗派分裂而大塊崩解 |
| 南亞（印度） | 婆羅門教/印度教階級（Dharma） | 權力分離：國王（剎帝利）掌武力，祭司（婆羅門）地位更高 | 政權更迭頻繁，底層村落/種姓制度幾千年不變 |

### 使用者提出的 schema 提案

在 `regimes` 加入 `legitimacy_type`（合法性基礎）與 `civilization_sphere`（文明圈）欄位（另有 `religion`），範例：

```json
{
  "regime_id": "tang-dynasty",
  "name": "唐",
  "civilization_sphere": "east-asian-confucian",
  "legitimacy_type": "mandate-of-heaven",
  "religion": "buddhism-daoism"
}
```

搭配的功能構想：地圖「圖層著色模式切換」——預設按政權著色，切換後按宗教/文明圈著色，8 世紀的世界會被清楚劃出儒佛圈/基督教圈/伊斯蘭圈。

## 六、鑑別分析：為什麼不該做成 `regimes` 的固定欄位

**核心問題：合法性基礎/宗教不是政權存續期間的固定值，會在同一個 `regimes` row 的生命週期內變動**——這是 `regime_territories` 當初被拍板為「快照表，不是一筆涵蓋全朝代」的同一個理由，套用到宗教/合法性基礎一樣成立：

- **君士坦丁皈依基督教（313/380 年）**：羅馬帝國沒有換政權（同一個 `regimes` row），但 legitimacy OS 從多神教換成基督教——政權存續期間的劇變，不是固定屬性。
- **唐朝的宗教搖擺**：李唐皇室自稱老子後裔尊道教，同時大力扶植佛教，845 年會昌滅佛又整肅佛教——同一個「唐」政權，`religion` 在不同時間點答案不同。
- **蒙古帝國是最極端的例子**：成吉思汗的帝國起於薩滿信仰的部落聯盟，分裂出的汗國卻走向完全不同的合法性系統——伊兒汗國、欽察汗國皈依伊斯蘭教，元朝在中國本部同時扶植藏傳佛教、又靠儒家天命觀取得漢地統治合法性，單一政權同時疊了兩套 legitimacy OS。「一個政權一個 `legitimacy_type` 欄位」在這個案例直接崩潰。

**第二個問題：使用者提出的分類表，套到專案自己的旗艦案例就已經漏了**：R2 的招牌案例是「西元 7-8 世紀，唐朝＋阿拉伯帝國」，但這個時間點的地圖上，唐朝跟大食之間還夾著**薩珊波斯**（祆教/瑣羅亞斯德教為國教），不屬於中原/歐洲基督教/伊斯蘭/南亞任何一類；再往北還有**可薩汗國**（統治階層改宗猶太教）、**回鶻汗國**（摩尼教為國教）。這些都是真實存在、且剛好落在專案自己最常引用的時空範圍內的反例——證明這類分類不能是寫死的小型 enum，得是像 `event_tags`／`observer_categories` 那種可以隨時插入新值的受控詞彙表。

## 七、若 M4 真的要做：建議的正確形狀

- **地圖著色功能需求本身保留、值得做**，但資料來源不該是 `regimes` 的固定欄位，而應比照 `regime_territories` 做**時間切片**——政權在某個時間區間屬於哪個文明圈/宗教陣營，是隨時間可能變動的快照，不是政權的固定屬性。
- **具體的信仰轉換事件（君士坦丁皈依、會昌滅佛）本來就該進 `historical_events`**——這套機制已支援標籤、多重視角、爭議點，比「一個固定欄位」更適合承載「這次轉換的史料考據與爭議」，不需要新概念。
- **`civilization_sphere` 若真要做，該是可擴充的受控詞彙表**，不是寫死 4-5 個值的 enum/CHECK constraint（薩珊波斯／可薩／回鶻反例已證明固定小分類不夠用）。
- **這類分類判斷要走既有的 citation 治理**（`docs/data-governance.md`）——「這個政權屬於哪個文明圈」在很多邊界案例上是史學家會爭論的判斷，不是客觀事實，應該跟 `historical_event_controversies` 一樣留有據可查的來源，不能由系統自己下定論。

## 八、彙整：M4 前必須處理的缺口清單（截至 2026-08-28）

- [ ] `predecessor_regime_id` 單一 FK 無法表達「多對一合併」（§三，例：英格蘭+蘇格蘭→大不列顛）。
- [ ] 「政權身份」與「統治家族」現在焊在同一實體，羅馬/拜占庭這類案例可能需要獨立概念，需等實際建置時再評估是否要加查詢表（§四）。
- [ ] 若要做「文明圈/宗教著色」地圖功能：資料須為時間切片、`civilization_sphere` 須為可擴充受控詞彙表，且需納入既有 citation 治理（§六、§七）。

## 九、神話算不算歷史的一環？（2026-08-28 第三輪）

延續 §五-§七 對「宗教/合法性基礎」的討論，使用者提出更根本的問題：神話算不算歷史？

### 結論：分兩層，不是一刀切的是/否

**神話當「客觀發生的事」——不算，不進 `regimes`/`regime_territories`**：堯的「疆域」、天照大神「創造」日本這類內容，沒有可考證的地理/文獻依據，無法通過 `docs/data-governance.md` 的治理標準（每筆正式資料要能追溯 title/author/locator/evidence）。這類內容落在憲法 §1「史前歷史先等整個完成後再處理」的既有排除範圍，不是新問題。

**神話當「政權拿來自我合法化的敘事」——算，且系統已有現成容器**：「曹丕援引堯舜故事」「天皇自稱天照大神後裔藉此拒絕易姓革命」「凱撒家族（Julii）自稱是維納斯之子埃涅阿斯的後裔」——這些不是神話本身，是「某個真實、可考證的政權**使用**了某段神話來鞏固合法性」，這件事本身是可考證的政治史事實，直接對應既有的 `historical_event_perspectives.official_justification` 欄位，不需要新結構。

### 一個自我指涉的具體例證

憲法 §4 狀態機的中文術語「禪讓」（現已改中立代碼 `succeeded`），其起源範式正是堯讓位給舜、舜讓位給禹的傳說——堯舜本身是半傳說人物，活動年代普遍認為早於中國最早有直接文字證據的商代甲骨文（約西元前 1200 年）。但曹丕篡漢時，史料明確記載他刻意援引堯舜故事包裝這次禪讓的正當性——這個「援引」本身是真實發生、有史料佐證的歷史事實，即使被援引的堯舜故事本身是神話。這正好示範了上述兩層區分：堯舜本身不進系統，「曹丕援引堯舜」進 `historical_event_perspectives`。

### 灰色地帶（不用現在解，留待 M4/M5）

有些政權介於「純神話」跟「可考證歷史」之間——夏朝（傳統紀年約西元前 2070-1600 年，二里頭文化考古佐證有限但存在，史學界對「夏朝」是否等於二里頭仍有爭論）、大和王權早期、羅馬建城傳說（傳統紀年前 753 年 vs 考古實際聚落年代）。這些不是「純神話」也不是「無爭議史實」，是史學界自己都還在辯論的史學問題本身——適合走 `historical_event_controversies`（一個政權的建國年代/存在本身是否成立，中立描述考古派 vs 文獻派各自主張），不需要系統替使用者下定論說某個早期政權「存在」或「不存在」。

### 落地驗證（2026-08-28）：補進既有種子資料

`event-han-abdicates-wei-220`（漢禪魏，2026-08-28 第一次補充新增）先前只有轉換邊連結跟正統性爭議點，沒有 `historical_event_perspectives`。已補上一筆魏方視角的 perspective，`official_justification` 具體引用堯舜禪讓典故作為正當性依據——這是既有 seed 資料裡第一筆真正的「政權援引神話自我合法化」案例，驗證 `official_justification` 欄位確實能承載這類內容，不需要新欄位。同時新增 `event_tags` 一筆「神話援引」（myth invocation），作為跨文明比較的可擴充標籤——未來若要在地圖上比較「哪些文明更依賴神話/天命合法化、哪些更依賴軍事/選舉合法化」，可以直接用這個標籤跨政權查詢，不需要等到 §六、§七 的 `civilization_sphere` 大改動才能做初步比較。

## 十、文明曆法（Calendar Systems）與西元年對應（2026-08-29，起於 task 2.2 EDTF 實作）

延續 task 2.2（EDTF 解析改用 `NodaTime` 負責曆法數學，見 implementation plan 2.2）的實作經驗，使用者追問：每個文明是否都有自己的曆法？能否都對應到西元年？資料庫有沒有對應的 mapper？

### 「曆法」跟「紀年標籤」是兩層不同的問題，容易混在一起

- **計日系統（曆法本身）**：決定「今天是哪一天」的規則——陽曆（格里曆、儒略曆、波斯曆）、陰曆（伊斯蘭曆，純月相、不跟太陽年校正，故齋戒月每年在陽曆上漂移約 11 天）、陰陽合曆（中國農曆、希伯來曆，靠插入閏月對齊太陽年）。
- **紀年標籤（疊加在某個曆法之上，不是獨立曆法）**：中國/日本年號（貞觀、開元、令和）、伊斯蘭教曆紀元（AH，從穆罕默德遷徙麥地那算起）、羅馬建城紀年（AUC）——這不是計日系統，是「怎麼稱呼某一年」的命名慣例，底層還是要靠某個曆法計日。`reign_eras` 表（§5 已拍板）處理的正是這一層，不涉及曆法轉換本身。

### NodaTime 部分填補、不是完全填補

查證 `NodaTime.CalendarSystem` 原始碼確認內建支援：`Julian`、`Coptic`、`Badi`（巴哈伊曆）、`Islamic`（多種變體，經 `GetIslamicCalendar` 帶 leap-year pattern/epoch 參數）、`Persian`（Simple/Arithmetic/Astronomical 三種變體）、`Hebrew`（Civil/Scriptural 兩種月份編號）——剛好對上這份筆記已經討論過的薩珊波斯（祆教/波斯曆）、阿拉伯帝國（伊斯蘭曆）等文明，換算數學不用自己刻。

**但缺口仍在**：
- **中國農曆完全沒有**——這是東亞第一階段自己最相關的曆法，卻是陰陽合曆裡最複雜的一種（閏月插入依二十四節氣動態計算，非固定週期公式，且曆法規則本身隨朝代改制而變），`NodaTime` 沒有內建，需要另外找中國農曆專屬套件或自己刻。
- **中美洲曆法（馬雅長紀曆、阿茲特克曆）完全沒有**——不屬於猶太-基督教-伊斯蘭這條共同曆法譜系，`NodaTime` 沒有，目前也沒查到現成 .NET 套件。
- **就算某個曆法有支援，也不代表涵蓋所有歷史變體**——例如伊斯蘭曆歷史上有「觀測月相起始」與「算術推算起始」兩種傳統，`NodaTime` 提供的是算術推算版本，是否貼合特定史料使用的實際慣例，需要真的有史料需求時另外驗證，這裡沒有進一步查證。
- **上古/傳說時代的曆法換算不是技術問題**——回到 §九「灰色地帶」的夏朝/三星堆案例：這種情況下「西元哪一年」本身就是史學界還在辯論的問題，任何曆法函式庫都解決不了，是史料考據問題不是工程問題。

### 更根本的一點：schema 目前完全沒有曆法轉換的欄位，工具支援不會自動補上

`historical_events.start_edtf`/`end_edtf` 存的是 EDTF 字串，而 **EDTF 規格本身只定義公曆**，沒有曆法系統標記欄位。現有 seed 資料的年份隱含假設「已經是換算成公曆的結果」，原始史料如果是用其他曆法記載，這個轉換過程完全沒有留下痕跡——連「這筆資料原始是哪個曆法、用什麼方法換算」都無法回答。這不會因為 `NodaTime` 支援某個曆法就自動解決：函式庫只解決「如果知道原始曆法，怎麼正確換算」，schema 要不要留欄位記錄「原始曆法是什麼」是完全獨立的設計決策。

這其實是 `docs/data-governance.md` 已經原則性要求、但還沒有結構化落地的東西——文件裡「Evidence note：此來源支持哪個名稱、時間...以及必要的轉換說明」這句話理論上該包含曆法轉換說明，但目前只是自由文字，不是資料庫欄位。正式匯入非中國史料（尤其伊斯蘭世界、波斯）前，這塊需要認真補：至少要決定「原始曆法系統」「原始曆法下的日期字串」「轉換方法/採用的曆法變體」要不要獨立成結構化欄位，還是先留在未來 citation model 的自由文字 evidence note 裡。

### 結論（截至 2026-08-29）

三個坑（曆法數學、schema mapper、上古紀年不確定性），`NodaTime` 只解決了第一個裡的一部分（伊斯蘭/波斯/希伯來，不含中國農曆與中美洲曆法）。schema mapper 完全沒做，上古紀年不確定性本質上無法用工具解決。全部列為 M4 世界史階段的開放問題，M2/M3（中國史範圍）不受影響。

## 十一、領域內容本身的多語言儲存（2026-08-29，起於 task 2.0 訊息代碼修訂）

延續 §十的曆法討論，使用者追問「語系」會不會影響其他 M1-M4。釐清後發現這其實是三個不同層次的「語言」問題，容易混在一起：

1. **系統訊息代碼**（task 2.0 這次修訂的範圍）——`ApiResponse.message` 這種少量、固定、可窮舉的系統文字，已改成穩定代碼，前端建對照字典即可（見 implementation plan Phase 3 任務 3.14a）。
2. **領域內容本身的語言**（這節要記的開放問題）——`regimes.self_name`、`historical_event_perspectives.narrative_summary`/`official_justification` 這些欄位現在都是**單一 TEXT 欄位，只能存一種語言**，內容本身是史料/敘事，數量大、每筆不同，不是能窮舉對照表解決的問題。
3. **程式碼/文件語言**（XML doc comment、OpenAPI 描述）——給開發者看的，跟前兩者是不同層次，現階段不需要處理。

**確認：多語系（真正的 UI 語言切換）目前不是已拍板的產品目標**——憲法從頭到尾沒有提到語言/i18n 相關的業務需求，這是這次技術決策附帶的架構彈性，不代表專案承諾要做語言切換功能。

**第 2 點是 M4 才會真正撞到的問題，現在標記、不預先設計**：中國史（M2/M3）範圍內敘事內容只有中文，不受影響。M4 若要呈現非中文史料（例如阿拉伯文原始文獻），會出現「原文＋翻譯」是否要並存的問題——現有 schema 完全沒有結構能裝這個（不像 `regime_aliases` 至少有自稱/他稱的多筆記錄設計，`narrative_summary` 這類欄位是單筆單語言）。要不要做、怎麼做（獨立語言變體表？JSONB 存多語言鍵值？只存原文語言＋另開翻譯表？）都還沒討論，留給 M4 實際遇到需求時再評估，這裡只記錄「這是一個存在但還沒設計」的缺口，不預先選一個方案。
